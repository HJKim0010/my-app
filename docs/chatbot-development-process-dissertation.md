# 챗봇 제작 과정 정리

## 1. 제작 목적과 기본 방향

본 연구에서 사용한 챗봇은 영어 학습자의 이야기 이어쓰기 과제를 지원하기 위해 제작된 제한적 쓰기 보조 도구이다. 챗봇의 목적은 학습자가 원문 또는 영상 자료를 이해하고, 자신의 이어쓰기 아이디어를 발전시키며, 문장 표현이나 구성에 대한 도움을 받을 수 있도록 하는 데 있었다. 그러나 학습자의 최종 산출물을 대신 작성하지 않도록 지원 범위를 명확히 제한하였다. 따라서 챗봇은 전체 이어쓰기 답안, 다음 문단, 모범 답안, 전체 초안 재작성, 전체 문장 번역과 같이 학습자의 저작권과 수행 과정을 대체할 수 있는 요청에는 직접 응답하지 않도록 설계되었다.

초기 제작 단계에서는 챗봇을 단순한 질의응답 도구가 아니라, 연구 과제의 조건을 유지하는 쓰기 지원 시스템으로 정의하였다. 즉, 챗봇은 과제 자료에 근거하여 응답하되, 학습자의 이어쓰기 방향과 표현 의도를 존중해야 했다. 이러한 목적에 따라 챗봇의 역할은 다음과 같이 설정되었다. 첫째, 학습자의 현재 질문에 직접 답한다. 둘째, 원문 또는 영상 자료와 관련된 이해 질문에는 자료 기반으로 답한다. 셋째, 아이디어, 구성, 어휘, 문장 표현, 피드백 요청을 제한된 범위 안에서 지원한다. 넷째, 학습자가 작성해야 할 최종 이어쓰기 내용은 학습자 자신이 구성하도록 남겨 둔다.

## 2. 전체 시스템 구조

챗봇은 Next.js 기반 웹 애플리케이션으로 구현되었다. 프론트엔드는 `app/page.tsx`에서 구현되었고, 사용자의 입력, 과제 선택, 참여자 ID, 세션 상태, 최근 대화 기록, 응답 스트리밍 화면 표시를 담당하였다. 사용자가 메시지를 입력하면 프론트엔드는 `/api/chat` 엔드포인트로 요청을 전송한다. 이 요청에는 과제 ID, 참여자 ID, 현재 질문, 최근 대화, 과제 조건, 세션 ID, 상호작용 횟수 등이 포함된다.

백엔드의 핵심 처리는 `app/api/chat/route.ts`에 구현되었다. 이 경로에서는 사용자의 요청을 분석하고, 정책 위반 여부를 판단하며, 필요한 경우 과제 자료를 검색하고, OpenAI Responses API를 호출하여 응답을 생성한다. 또한 응답 생성 과정에서 사용된 검색 자료, 정책 판단, 응답 상태, 세션 정보 등을 로그로 저장한다.

시스템의 전체 흐름은 다음과 같다.

1. 학습자가 챗봇 인터페이스에서 질문 또는 요청을 입력한다.
2. 프론트엔드는 현재 과제, 참여자, 세션, 최근 대화 맥락을 포함하여 서버로 요청을 보낸다.
3. 서버는 요청의 범위와 의도를 분석한다.
4. 요청이 제한된 범위에 해당하면 미리 정의된 리다이렉트 응답을 반환한다.
5. 허용된 요청이면 대화 기억과 과제 자료를 바탕으로 필요한 맥락을 구성한다.
6. 과제 자료 지식이 필요한 경우 RAG 방식으로 관련 자료를 검색한다.
7. 시스템 지시문과 사용자 입력 프롬프트를 구성하여 OpenAI 모델에 전달한다.
8. 생성된 응답을 스트리밍 방식으로 프론트엔드에 표시한다.
9. 요청, 응답, 정책 판단, 검색 정보, 세션 정보를 로그로 저장한다.

## 3. 과제 자료 구성과 조건 분리

챗봇은 두 개의 이어쓰기 과제를 지원하도록 구성되었다. 참여자 화면과 연구 서술에서는 각각 Story A와 Story B로 표기하고, 코드상에서는 `task1`과 `task2`로 구분한다. 기존 로그 호환성을 위해 내부 저장값은 각각 `ep1`, `ep2`로 매핑된다. 각 과제는 정적 조건과 동적 조건을 모두 지원한다. 정적 조건은 원문 텍스트, 이미지 설명, 오디오 전사 자료를 포함하고, 동적 조건은 영상 전사 자료와 장면 라벨을 포함한다.

각 과제의 설정은 `data/task1/task.json`과 `data/task2/task.json`에 저장되었다. 두 과제 모두 `restricted_source_grounded_bounded_support` 조건을 사용하며, 이는 챗봇이 자료 기반으로 제한된 지원만 제공해야 함을 의미한다. 정적 조건에서는 `source_text`, `audio_transcript`, `image_description`, `prompt`, `instruction`이 허용 자료로 설정되었다. 동적 조건에서는 `video_transcript`, `scene_labels`, `prompt`, `instruction`이 허용 자료로 설정되었다.

이러한 구조는 연구 조건 간의 자료 차이를 유지하기 위한 것이다. 학습자가 정적 조건에 배정된 경우에는 읽기 자료와 이미지/오디오 기반 자료가 중심이 되고, 동적 조건에 배정된 경우에는 영상 전사와 장면 정보가 중심이 된다. 챗봇은 현재 선택된 과제와 조건에 해당하는 자료만 불러오도록 설계되었다.

## 4. RAG 기반 자료 검색 구조

챗봇은 과제 자료에 근거한 응답을 제공하기 위해 검색 증강 생성(Retrieval-Augmented Generation, RAG) 방식을 사용하였다. 관련 코드는 `backend/rag` 폴더에 나누어 구현되었다. `loader.ts`는 과제 설정과 자료를 불러오고, `chunker.ts`는 자료를 검색 가능한 단위로 분할하며, `retriever.ts`는 사용자의 질문과 관련성이 높은 자료 조각을 선택한다. 또한 `lexicon.ts`와 과제별 lexicon 파일은 등장인물, 사물, 장소, 사건 단서를 인식하고 검색 성능을 보완하는 데 사용되었다.

초기에는 자료 검색이 비교적 넓게 실행될 수 있었으나, 제작 과정에서 검색이 항상 필요한 것은 아니라는 문제가 확인되었다. 예를 들어 학습자가 단순히 특정 문장을 영어로 표현하고 싶다고 요청한 경우, 이전 대화에 나온 장소나 사건이 검색되어 현재 요청을 방해할 수 있었다. 이에 따라 검색은 현재 요청이 원문 또는 영상 자료 지식을 필요로 할 때만 실행되도록 점차 조정되었다. 현재 구조에서는 요청 분류 결과가 자료 맥락을 요구할 때 `targeted_rag` 또는 `canonical_plus_rag` 방식으로 자료가 프롬프트에 포함된다.

또한 원문 사실과 학습자의 창작 아이디어가 섞이지 않도록 프롬프트에 별도의 지시가 추가되었다. 챗봇은 원문에 명시된 사실, 학습자가 제안한 이어쓰기 설정, 챗봇이 제안한 가능성, 현재 질문을 구분해야 한다. 원문에 명시되지 않은 내용은 사실처럼 말하지 않고, 필요한 경우 "해석" 또는 "가능한 전개"로 표시하도록 설계되었다.

## 5. 정책 분류와 제한 응답

챗봇의 핵심 설계 원칙 중 하나는 학습자의 최종 산출물을 대체하지 않는 것이다. 이를 위해 `backend/policy/classifier.ts`에서 사용자의 요청을 분석하고, 제한된 요청인지 허용 가능한 지원 요청인지 판단하였다. 제한 요청의 주요 범주는 다음과 같다.

- `sentence_generation`: 전체 이어쓰기, 다음 문단, 모범 답안, 완성 답안 생성 요청
- `draft_rewrite`: 전체 초안 또는 문단 전체를 다시 써 달라는 요청
- `direct_translation`: 학습자가 작성해야 할 한국어 문장 전체를 완성된 영어 문장으로 번역해 달라는 요청
- `outside_content`: 과제와 무관한 외부 지식 요청
- `scoring_evaluation`: 점수, 등급, rubric band와 같은 평가 요청

제한 요청으로 판단되면 OpenAI 모델이 자유롭게 응답하지 않고, `backend/policy/redirect.ts`에 정의된 리다이렉트 응답이 반환된다. 리다이렉트 응답은 단순히 거절하는 방식이 아니라, 허용 가능한 대체 지원을 제안하는 방식으로 작성되었다. 예를 들어 전체 문단을 써 달라는 요청에는 문단을 대신 작성하지 않고, 아이디어 정리, 사건 순서, 핵심 표현, 한 문장 피드백과 같은 제한된 도움을 제공할 수 있다고 안내한다.

제작 과정에서 번역 정책은 여러 차례 조정되었다. 초기에는 한국어 문장을 영어로 바꾸는 요청이 지나치게 제한적으로 처리될 위험이 있었고, 반대로 완성 문장을 제공하면 학습자의 최종 답안 작성 과정을 대체할 위험이 있었다. 최종적으로는 짧은 단어와 구, 국소적 표현, 문장 구조 도움은 허용하되, 전체 답안을 대신하는 수준의 번역이나 문단 생성은 제한하는 방향으로 정리되었다. 특히 학습자가 특정 의미를 영어로 어떻게 말하는지 묻는 경우에는 문장 수준의 표현 도움을 제공할 수 있도록 조정되었다.

## 6. 대화 기억과 현재 요청 우선순위

챗봇이 일반적인 대화형 AI처럼 자연스럽게 작동하기 위해 최근 대화 맥락을 활용하도록 설계하였다. 프론트엔드는 현재 과제의 최근 메시지를 서버로 보내고, 백엔드는 `backend/rag/conversationMemory.ts`에서 최근 대화 요약, 전체 대화 요약, 마지막 사용자 초점, 활성 등장인물/사건, 현재 작업 맥락 등을 구성한다. 최근 대화는 짧은 후속 질문, "그거", "다시", "좀 더", "왜?"와 같은 맥락 의존적 표현을 해석하는 데 사용된다.

그러나 제작 과정에서 대화 기억이 오히려 현재 요청을 방해하는 문제가 나타났다. 이전 대화에서 특정 장면이나 사건을 다루고 있었을 때, 학습자가 새로운 문장 표현을 요청했음에도 챗봇이 이전 주제로 돌아가 답하는 경우가 있었다. 예를 들어 학습자가 새롭게 어떤 메시지를 남긴 사람에 대해 영어로 표현하고 싶다고 했는데, 챗봇이 이전 대화의 카페, 테이블 7, 행동 순서 맥락을 이어 받아 응답하는 문제가 확인되었다.

이 문제를 해결하기 위해 현재 요청 우선순위를 강화하였다. `backend/rag/contextPriority.ts`와 `conversationMemory.ts`에는 새로운 언어 표현 요청을 감지하는 규칙이 추가되었고, 이러한 요청은 이전 대화의 이어쓰기 맥락으로 끌려가지 않도록 수정되었다. 또한 프롬프트에는 `CURRENT_USER_REQUEST`가 `RELEVANT_CHAT_HISTORY`보다 우선한다는 지시가 명시되었다. 즉, 최근 대화는 현재 질문의 지시어나 짧은 후속 표현을 해석하는 데만 사용하고, 현재 질문이 새로운 요청인 경우에는 현재 질문을 중심으로 답하도록 설계하였다.

## 7. 프롬프트 설계

프롬프트 구성은 `backend/rag/promptBuilder.ts`에서 관리된다. 시스템 지시문은 챗봇의 역할, 허용/제한 범위, 자료 근거 사용 방식, 학습자 아이디어와 원문 사실의 구분, 응답 톤, 대화 맥락 사용 원칙을 포함한다. 사용자 입력 프롬프트는 구조화된 섹션으로 구성되며, 과제 정보, 지원 모드, 작업 맥락, 대화 기억, 학습자 초안, 검색된 자료, 현재 요청을 분리하여 모델에 전달한다.

프롬프트 제작 과정에서 가장 중요한 변화는 챗봇이 "과제 감독자"처럼 행동하지 않도록 조정한 점이다. 초기 응답은 학습자의 질문에 답한 뒤에도 계속 다음 단계나 과제 수행 방향을 제안하는 경향이 있었다. 이후 프롬프트에는 "현재 질문에 먼저 답할 것", "학습자가 요청하지 않은 다음 단계로 밀어붙이지 말 것", "자료 요약이나 과제 안내를 불필요하게 반복하지 말 것"이라는 지시가 추가되었다.

또한 지원 모드별 지시문이 세분화되었다. 이해 지원에서는 자료 사실을 간단히 설명하고, 아이디어 지원에서는 가능한 전개를 옵션으로 제시하되 확정 사실처럼 말하지 않으며, 구성 지원에서는 사건 순서나 흐름만 간단히 제안한다. 언어 지원에서는 단어, 구, 문장 표현을 국소적으로 도와주고, 피드백 지원에서는 학습자가 작성한 문장의 의미를 유지하면서 문법, 표현, 논리, 흐름을 점검한다.

## 8. 프론트엔드 인터페이스와 사용자 흐름

프론트엔드는 학습자가 과제에 진입하기 전에 참여자 ID를 입력하고, 안내 화면을 확인한 뒤 챗봇을 사용할 수 있도록 구성되었다. 과제는 Story A와 Story B로 분리되며, 각 과제는 별도의 대화 상태를 가진다. 따라서 Story A에서 나눈 대화가 Story B 요청에 섞이지 않도록 설계하였다.

인터페이스는 여러 차례 조정되었다. 초기에는 안내 문구, 예시 프롬프트 버튼, 과제 선택 흐름, 모바일 레이아웃, 채팅 입력창 위치, 스크롤 동작, 응답 가독성 등이 반복적으로 수정되었다. 특히 연구 참여자가 모바일이나 작은 화면에서 사용할 가능성을 고려하여 안내 카드와 채팅창 높이, 입력창 배치, 메시지 영역 스크롤, 버튼 표시 방식을 개선하였다.

응답 표시 방식도 변경되었다. 기존에는 응답이 한 번에 표시되는 방식이었으나, 이후 OpenAI 응답을 NDJSON 스트림으로 받아 프론트엔드에서 점진적으로 표시하도록 구현하였다. 이를 통해 사용자는 긴 응답이 생성될 때도 챗봇이 작동하고 있음을 즉시 확인할 수 있게 되었다.

## 9. 로그와 연구 데이터 저장

연구용 챗봇이므로 각 상호작용을 분석 가능한 형태로 저장하는 기능이 중요했다. 로그 처리는 `backend/logs/logger.ts`와 관련 API에서 구현되었다. 시스템은 참여자 ID, 세션 ID, 스토리 식별자, 조건, 사용자 질문, 정책 판단, 제한 사유, 검색된 자료 조각, 챗봇 응답, 응답 길이, 상호작용 횟수, 세션 지속 시간, 지원 모드, 검색 실행 여부 등을 저장한다.

Supabase 환경 변수가 설정되어 있으면 로그는 Supabase의 `chat_events`와 `session_transcripts` 테이블에 저장된다. Supabase가 설정되어 있지 않은 개발 환경에서는 로컬 JSONL 파일로 저장된다. 이 구조는 개발 중에는 로컬에서 테스트하고, 실제 연구 운영 시에는 서버 측 저장소에 데이터를 누적할 수 있도록 하기 위한 것이다.

또한 참여자 ID 저장과 스토리 식별자 매핑도 제작 과정에서 정리되었다. 초기에는 과제 ID와 내부 episode ID가 혼재될 수 있었으나, 이후 화면에서는 Story A/B로 표기하고 내부 로그에서는 `task1`과 `task2`를 각각 `ep1`과 `ep2`로 기록하도록 수정하였다. 세션 transcript 저장 기능도 추가되어, 개별 턴 로그뿐 아니라 세션 단위의 전체 대화 흐름을 분석할 수 있게 되었다.

## 10. 주요 변동 과정

챗봇은 한 번에 완성된 것이 아니라, 실제 테스트와 문제 발견을 통해 반복적으로 수정되었다. Git 기록을 기준으로 보면 2026년 3월에는 제한된 multimodal Task 1 챗봇을 구축하고, 자료 검색과 기본 리다이렉트 정책을 마련하는 작업이 이루어졌다. 이후 과제 자료 이해, lexicon 기반 검색, mixed Korean-English 질문 처리, 과제 선택 흐름, 참여자 ID, 로그 저장 기능이 차례로 추가되었다.

2026년 4월에는 대화형 사용성을 개선하는 작업이 진행되었다. 짧은 후속 질문, 언어 전환, 모바일/태블릿 안내 화면, 과제 안내 문구, 구조 설명, 후속 질문 처리 등이 조정되었다. 이 시기에는 챗봇이 단순히 자료를 검색하는 시스템에서 학습자의 대화 흐름을 따라가는 시스템으로 확장되었다.

2026년 5월에는 한국어 안내문, 번역 리다이렉트, prompt bubble, quick reply, Supabase 로그 안정화, 응답 길이 문제 등이 수정되었다. 챗봇의 UI도 보다 단순하고 일관된 형태로 정리되었다.

2026년 7월에는 가장 많은 변동이 있었다. 챗봇의 정책, 라우팅, 대화 기억, 현재 요청 우선순위, source grounding, feedback, streaming, mobile layout, guide navigation 등이 집중적으로 수정되었다. 특히 챗봇이 이전 대화 맥락을 과도하게 따라가거나, 학습자의 현재 표현 요청을 이전 이야기 전개 요청으로 잘못 분류하는 문제를 해결하기 위한 수정이 이루어졌다. 또한 학습자가 자신의 영어 문장이나 문단을 입력했을 때 피드백 요청으로 해석하고, source fact와 learner-created continuation을 구분하도록 조정하였다.

2026년 8월에는 현재 요청을 우선하는 intent-first routing이 추가로 개선되었다. 이는 챗봇이 과거 대화나 검색 자료보다 학습자의 최신 발화를 먼저 해석하도록 하기 위한 최종 안정화 작업에 해당한다.

## 11. 검증과 회귀 테스트

챗봇의 동작을 안정화하기 위해 여러 회귀 테스트 스크립트가 작성되었다. `scripts/policy-regression-tests.mjs`는 제한 요청과 허용 요청이 의도대로 분류되는지 확인한다. 예를 들어 전체 문단 작성, 모범 답안, 점수 평가 요청은 제한되어야 하고, 표현 도움, 문장 피드백, 자료 이해 질문은 허용되어야 한다.

`scripts/context-priority-tests.mjs`는 최근 대화 맥락이 현재 요청을 잘못 덮어쓰지 않는지 확인한다. 특히 이전 대화에서 특정 장면을 다루었더라도, 새롭게 들어온 한국어 표현 요청은 언어 지원으로 처리되어야 하며 이전 주제의 후속 질문으로 분류되지 않아야 한다. 이 테스트는 실제 제작 과정에서 발견된 맥락 오류를 재발하지 않도록 하기 위해 추가되었다.

그 외에도 streaming, conversation continuity, writing assistant behavior, conversation planner self-audit 등과 관련된 테스트 스크립트가 포함되어 있다. 이러한 테스트는 챗봇이 정책적으로 제한된 범위를 유지하면서도 학습자의 질문에 자연스럽게 반응하는지 확인하기 위한 보조 장치로 사용되었다.

## 12. 최종 구현 상태

최종적으로 챗봇은 다음과 같은 기능을 갖춘 연구용 쓰기 보조 시스템으로 정리되었다.

- Story A와 Story B 과제 분리
- 정적 조건과 동적 조건에 따른 자료 분리
- 자료 기반 RAG 응답
- 한국어, 영어, 혼합 언어 요청 처리
- 이해, 아이디어, 구성, 언어 표현, 피드백 지원
- 전체 답안 생성, 문단 작성, 전체 초안 재작성, 평가 요청 제한
- 긍정적 리다이렉트 응답
- 현재 요청 우선 대화 라우팅
- 최근 대화 기억과 세션 단위 기억
- 스트리밍 응답 표시
- 참여자 ID와 세션별 로그 저장
- Supabase 또는 로컬 JSONL 저장
- 정책 및 맥락 우선순위 회귀 테스트

이러한 제작 과정은 연구 목적에 맞는 균형을 찾는 과정이었다. 챗봇은 학습자에게 충분히 유용해야 했지만, 동시에 학습자의 최종 글쓰기를 대신해서는 안 되었다. 또한 자료 기반성을 유지해야 했지만, 모든 요청에 자료 검색을 과도하게 적용하면 현재 표현 요청이나 피드백 요청을 방해할 수 있었다. 따라서 최종 설계는 자료 근거, 쓰기 지원, 정책 제한, 대화 자연성, 연구 데이터 수집이라는 다섯 요소를 조정하는 방향으로 발전하였다.

## 13. 논문 서술용 요약문

본 연구의 챗봇은 영어 이야기 이어쓰기 과제를 지원하기 위해 Next.js 기반 웹 애플리케이션으로 제작되었다. 챗봇은 두 개의 과제와 정적/동적 자료 조건을 구분하여 운영되며, 원문 텍스트, 오디오 전사, 이미지 설명, 영상 전사, 장면 라벨 등 조건별 자료를 기반으로 응답하도록 설계되었다. 백엔드에서는 사용자의 요청을 분석하여 이해, 아이디어, 구성, 언어 표현, 피드백 등 허용 가능한 지원 유형을 분류하고, 필요한 경우 RAG 방식으로 관련 과제 자료를 검색하여 OpenAI 모델에 전달하였다.

챗봇의 핵심 원칙은 학습자의 이어쓰기 수행을 보조하되 최종 산출물을 대신 작성하지 않는 것이다. 이를 위해 전체 이어쓰기, 다음 문단 작성, 모범 답안 생성, 전체 초안 재작성, 평가 점수 제공과 같은 요청은 제한하고, 대신 아이디어 정리, 사건 흐름 점검, 표현 선택, 문장 수준 피드백 등 작은 단위의 지원으로 전환하였다. 또한 대화 기억 기능을 포함하여 짧은 후속 질문을 처리하도록 했으나, 제작 과정에서 이전 대화 맥락이 현재 요청을 방해하는 문제가 발견되어 현재 사용자 요청을 최우선으로 처리하도록 라우팅과 프롬프트를 수정하였다.

최종 시스템은 참여자 ID와 세션 ID를 기반으로 대화를 분리하고, 각 상호작용의 사용자 질문, 정책 판단, 검색 자료, 응답, 세션 정보를 로그로 저장한다. Supabase가 설정된 연구 환경에서는 로그가 데이터베이스에 저장되고, 개발 환경에서는 로컬 JSONL 파일로 저장된다. 제작 과정 전반에서는 정책 분류, 현재 요청 우선순위, 대화 연속성, 스트리밍 응답 등에 대한 회귀 테스트를 작성하여 챗봇의 안정성을 점검하였다.
